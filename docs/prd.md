# 产品需求文档：企业 Agent Runtime 与项目风控工作台

- 文档状态：Baseline v1
- 产品阶段：架构原型完成，进入可靠业务闭环建设
- 目标岗位：AI 前端工程师、AI 全栈工程师

## 1. 产品定义

本项目为企业 PaaS 提供可复用的 Agent 执行与治理能力，并以“项目风控与供应商准入尽调”为首个标杆场景。

风控人员提交项目和供应商后，Risk Agent 在租户与对象权限范围内读取业务数据、检索企业制度、动态补充证据、生成可追溯的风险结论；所有产生业务副作用的操作必须经人工确认，审批后才能创建整改任务。Web 工作台和 React Native 客户端通过统一 Run API 与事件协议接入同一 Runtime。

本项目不是聊天机器人、通用 Coze 平台或模型训练平台。核心价值是让 AI 安全进入现有企业业务流程。

## 2. 背景与问题

现有 PaaS 已有 AI 问答、表单生成和风险辅助等能力，但多数调用仍是“页面请求模型并展示文本”，存在以下缺口：

1. 业务数据分散在项目、供应商、审批、文档和第三方风险系统中。
2. 模型缺少统一工具权限，容易把“可调用”误当成“可授权”。
3. 结论与原始数据、制度条款之间没有稳定的引用关系。
4. 长任务在网络中断、App 切后台或服务重启后难以恢复。
5. 写业务对象缺少人工确认、幂等和审计闭环。
6. 不同 AI 场景重复实现事件、审批、工具和客户端接入逻辑。

## 3. 产品目标

### 3.1 业务目标

- 将一次供应商准入尽调收敛为可观察、可补充、可审批的标准流程。
- 每条风险结论都能定位到真实业务数据或企业制度原文。
- Agent 只提出和执行授权范围内的操作，写操作必须人工确认。
- Web 与 RN 共享任务、事件和审批状态，不重复运行 Agent。

### 3.2 工程目标

- 建立与具体业务无关的 Runtime、Tool Registry、Event Protocol 和 Evidence 模型。
- 支持任务暂停、进程重启后恢复、事件回放和幂等业务回写。
- 使用第二个轻量业务 Agent 验证平台能力可以复用，而不是复制代码。
- 建立可复现的评测集，所有简历指标来自实际运行结果。

## 4. 非目标

- 不建设可视化拖拽工作流、Prompt 商城或通用机器人市场。
- 不让模型直接生成并执行 SQL，不让客户端直接访问 Qdrant。
- 不训练或微调基础模型，不以算法工程师岗位为目标。
- 不在没有性能证据时引入 Redis、消息队列、微服务或 Kubernetes。
- 不用一个“万能 Agent”覆盖所有业务；平台运行多个边界清晰的业务 Agent。

## 5. 目标用户

| 用户 | 核心任务 | 权限边界 |
| --- | --- | --- |
| 风控专员 | 发起尽调、查看证据、补充材料 | 只能访问授权项目和供应商 |
| 风控负责人 | 审核风险结论、批准或驳回写回 | 需要审批 Scope，并记录意见 |
| 平台管理员 | 查看失败任务、工具审计和运行指标 | 不默认拥有业务数据内容权限 |
| PaaS 开发者 | 注册业务工具、接入新 Agent 和客户端 | 通过 Schema 与策略扩展，不改 Runtime 内核 |

## 6. 核心业务流程

### 6.1 正常尽调

1. 用户选择项目、供应商和重点风险维度并创建 Run。
2. Agent 生成结构化取证计划，只能选择 Registry 暴露的只读工具。
3. Runtime 并发执行允许的工具，将结果登记为 Evidence。
4. Agent 评估必需维度覆盖率；证据不足时生成补充计划。
5. 达到退出条件后，模型基于 Evidence 生成结构化 Finding。
6. 确定性校验器验证 Evidence 引用、业务规则和预算。
7. Run 暂停为 `waiting_approval`，工作台展示报告及将要执行的操作。
8. 审批通过后幂等创建整改任务；驳回或补充材料则进入对应分支。

### 6.2 异常与恢复

- 工具超时：记录失败、按策略重试或切换备用工具，不隐藏失败原因。
- 证据不足：最多执行规定轮数，仍不足则暂停等待人工补充。
- 客户端断线：使用最后 `sequence` 补发事件，不重新创建 Run。
- 服务重启：从 PostgreSQL checkpoint 恢复，不重复已确认的业务写入。
- 并发审批：数据库约束保证只有一个有效决策和一次业务副作用。

## 7. 功能范围

### P0：简历可演示的完整闭环

- `FR-001` 使用 JWT 建立可信租户、用户、角色和 Scope 上下文。
- `FR-002` 创建、查询、取消和恢复 Agent Run。
- `FR-003` 使用受约束动态 Loop 完成规划、取证、覆盖评估和补充规划。
- `FR-004` Tool Registry 统一处理 Schema、授权、超时、审计和写工具幂等。
- `FR-005` PostgreSQL 持久化 Run、checkpoint、事件、Evidence、Finding 和审批。
- `FR-006` Qdrant 按租户及权限标签检索制度 Chunk，返回可定位 Evidence。
- `FR-007` Web 工作台展示任务列表、执行时间线、风险报告、Evidence 和审批。
- `FR-008` SSE 支持实时事件、sequence 去重和断线补发。
- `FR-009` 提供确定性 Model Provider，使自动化测试不依赖外部模型。
- `FR-010` 提供真实 Model Provider，输出必须通过结构化 Schema 校验。

### P1：证明平台复用与 PaaS 特色

- `FR-101` 从 PaaS 业务对象元数据生成只读/写入 Tool Schema。
- `FR-102` Tool Registry 作为唯一执行入口，MCP Server 只作为协议适配层。
- `FR-103` React Native Agent SDK 支持鉴权、SSE、补发和生命周期恢复。
- `FR-104` 实现一个轻量合同合规 Agent，复用平台内核和工作台时间线。

### P2：评测与运营

- `FR-201` 建立脱敏案件、制度问题和跨租户攻击评测集。
- `FR-202` 展示任务成功率、引用正确率、恢复成功率、延迟和 Token 成本。
- `FR-203` 支持按 Run 查询节点、工具、审批和业务回写审计记录。

## 8. 工作台范围

工作台是风控业务客户端和协议参考实现，不是 Agent 搭建平台。首版只包含：

1. 尽调任务列表与状态筛选。
2. 创建尽调任务表单。
3. Run 详情：执行时间线、风险结论、Evidence 原文和失败诊断。
4. 人工审批：批准、驳回、要求补充材料及写回预览。

Web 使用 TanStack Query 管理服务端事实，Zustand 只管理 SSE 连接、事件投影和重连游标。RN SDK 不绑定状态框架，接入既有 RNModules 时使用项目已有 Redux 体系。

## 9. 成功指标

以下是验收目标，不是当前已取得的结果：

| 指标 | 目标 |
| --- | --- |
| 跨租户越权测试 | 0 条数据泄漏 |
| checkpoint 故障注入恢复 | 关键场景 100% 通过 |
| 同一幂等键业务写入 | 最多产生一次副作用 |
| Finding 引用有效性 | 100% 引用已登记 Evidence |
| 制度检索 Recall@5 | 在固定评测集上不低于 0.85 |
| 引用定位正确率 | 在人工标注集上不低于 0.90 |
| 客户端事件投影 | 重放与实时合并后无重复、无倒序状态回退 |

延迟、Token 成本和任务成功率在真实评测后记录基线，不提前承诺虚构数值。

## 10. 产品完成定义

项目只有同时满足以下条件，才能在简历中称为“企业 Agent Runtime 与 PaaS 智能业务执行平台”：

- 风控业务从发起到审批写回可以通过工作台完整演示。
- 服务重启、客户端断线和重复审批均有自动化验证。
- 跨租户访问在 API、数据库、工具和向量检索四层被阻止。
- Risk Agent 使用真实模型与真实知识检索，同时保留确定性测试模式。
- 第二个 Agent 复用平台能力，且 Runtime 内核没有出现第二个业务的领域字段。
- 指标、架构图、ADR、测试报告和演示脚本与代码保持一致。
