# 面试深挖手册

## 1. 项目定位

一句话：这是企业业务 Agent 的执行与治理 Runtime，不是聊天机器人，也不是 Coze 式通用搭建平台。

核心矛盾：模型擅长理解和规划，但企业系统要求权限可控、过程可追溯、写操作可审批、失败可恢复。因此模型只能提供候选决策，确定性代码掌握执行权。

## 2. 高频追问

### 为什么项目看起来没有那么复杂？

复杂度不在节点数量，而在跨边界正确性：模型输出能否执行、Evidence 是否支持 Finding、租户是否泄漏、审批是否竞争、写回失败能否恢复、客户端断线是否重复创建。项目用自动化故障注入、真实模型评测和第二 Agent 复用证明这些边界，而不是用更多页面或微服务制造复杂度。

### 自研 DAG 工作流引擎是什么？这里自研了吗？

这里没有宣称自研通用 DAG 引擎。图执行、checkpoint 和 `interrupt/Command(resume)` 使用 LangGraph；自研部分是企业运行治理：Agent Registry、受约束计划校验、Tool Registry、Evidence/Finding 规则、审批竞争、事件协议、幂等恢复和多租户边界。这样比重复实现图调度器更符合业务价值。

### Loop 是写死还是动态？

拓扑和安全边界固定，计划内容动态。模型动态选择本轮只读工具和缺失维度，代码固定白名单、参数构造、预算、三轮上限和退出条件。完全写死不能利用模型，完全动态又无法治理。

### 为什么用 LangGraph？

业务存在显式状态、多轮补证、人工中断和重启恢复，LangGraph 的状态图与 checkpoint 适合这些需求。简单问答或单次工具调用不需要它；如果没有人工中断和恢复，普通函数编排更轻。

### 为什么不用 Next.js？

工作台是登录后的内部操作界面，不需要 SSR、SEO、RSC 或文件路由。React + Vite 启动更直接，服务端状态由独立 Fastify API 管理。若后续需要 BFF、统一鉴权中间层或公网内容页，再评估 Next.js。

### 为什么用 Monorepo？

API、Web、Agent、协议、Runtime 和评测共享 TypeScript 契约，但部署边界仍清晰。Monorepo 让跨包重构和契约测试原子提交；当前规模不需要多仓版本发布。通过架构测试防止“同仓库等于随意依赖”。

### Zustand 是否必要？

只用于高频 SSE 事件投影和连接状态；服务端 Run 快照使用 TanStack Query，表单/弹窗使用 React 本地状态。它不是全局万能 Store，也不会持久化 Token 或代替服务端事实。

### 为什么 PostgreSQL 加 Qdrant？

PostgreSQL 保存文档版本、权限、Run 和审计事实；Qdrant 只保存可重建向量索引。文档与 Outbox 同事务提交，索引失败可重试。把 Qdrant 当事实源会难以处理事务、版本和审计。

### Qdrant 是必须的吗？

生产知识检索场景需要向量召回，所以使用 Qdrant；单元测试和快速 Demo 使用内存索引。系统通过 `VectorIndex` 端口隔离实现，不让 Agent 或客户端直接依赖 Qdrant。

### MCP 和 Tool Registry 有什么区别？

Tool Registry 是治理内核，负责 Schema、授权、审批、幂等、超时和审计；MCP 是工具发现和调用协议。MCP 调用仍进入同一个 Registry，不能绕过安全策略，也不能信任模型参数中的租户或审批信息。

### 和 Coze 有什么区别？

Coze 偏通用 Agent 搭建与运营平台；本项目聚焦企业内受控执行 Runtime，与既有 PaaS 权限、元数据、业务写回和多端协议结合。它不做拖拽编排、Prompt 商店和机器人市场。

### PaaS 元数据怎样变成工具？

PaaS 导出版本化脱敏快照，编译器先做运行时校验，再取字段可见性、字段权限、只读状态和敏感策略的交集，生成 get/create/update Zod Schema。元数据只定义能力上限，实际调用仍需可信 Identity 和对象权限。

### 多租户只靠 JWT 吗？

不够。JWT 建立可信身份；API 不接受请求体 tenantId；Repository 查询必须带租户条件；Tool Context 注入可信租户；Qdrant 查询带 tenant/permission filter；缓存和客户端 storageKey 也包含租户与用户。

### 如何防 Prompt Injection？

模型不能直接执行 SQL或任意工具；计划只允许 Registry 白名单；租户、Scope、审批凭据来自可信上下文；工具输入输出经过 Schema；检索内容作为不可信 Evidence，不提升权限；写操作必须人工审批和稳定幂等键。

### 如何保证 Finding 不胡说？

候选 Finding 必须通过 Zod，并引用已登记 Evidence；校验器检查 Evidence ID、风险维度和业务事实边界。E2 曾发现模型把制度条件当作案件事实，随后增加事实守卫和回归门禁，将引用准确率从 78.38% 提升到 100%。

### 为什么需要 Event Store？

Run 快照回答“现在是什么状态”，事件日志回答“怎么到这里”。持久化 sequence 支持审计、Web/RN 时间线、断线补发和故障分析；SSE 只是传输，不是事实源。

### SSE 如何避免丢事件？

客户端保存 `lastSequence`；恢复时先 `replay(after=N)`，再订阅 SSE；服务端在回放和订阅切换期间缓存事件并按 sequence 合并；客户端丢弃小于等于当前游标的重复事件。

### 为什么不用 WebSocket？

当前主要是服务端单向事件流，SSE 支持标准 HTTP、代理和断线语义，复杂度更低。若以后需要高频双向协作或二进制消息，再考虑 WebSocket。

### 审批并发怎么处理？

Approval 在数据库中原子竞争，只有一个调用成为有效决策；后续写工具必须携带批准人和稳定幂等键。其他并发调用返回可解释冲突，不会各自执行一次写回。

### 崩溃窗口怎么处理？

重点测试“下游写入成功，Run 尚未完成”窗口。恢复后依据审批事实和 checkpoint 继续，写工具复用相同幂等键并返回已有结果，再校准 Run。没有宣称任意下游都天然 exactly-once。

### RN 项目没有运行，跨端能力可信吗？

框架无关 Client Core 在真实 Web API/SSE 实验台完成生命周期链路；RN AppState 和存储由薄适配器及契约测试覆盖。可证明协议恢复和适配边界，但简历明确不宣称旧 RNModules 已完成真机系统杀进程验证。

### 为什么第二个 Agent 比再做一个复杂页面更重要？

第二 Agent 检验平台抽象是否真实：Contract Agent 接入时没有修改 Runtime 领域模型，也没有复制 Event Store、审批或幂等内核。它比单业务增加更多节点更能证明平台级能力。

### 评测为什么可信？

数据集有版本，指标由脚本生成，报告绑定 Git revision；E0/E1/E2 分层，E2 连续三轮并有回归门禁。可信不等于生产效果，合成数据和三轮窗口限制会主动写在报告与简历中。

### 为什么最终指标都是 100%，会不会太假？

数据规模小且领域限定，所以 100% 只能说明当前回归集全部通过。更有价值的是首次真实评测只有 78.38% 引用准确率和 75% 任务成功率，评测发现事实边界问题并推动修复。面试时优先讲这个改进过程。

### 当前最大技术债是什么？

异步 Run 仍使用进程内调度；创建后立即宕机缺少持久化执行队列接管。Run、Event 和产物尚未形成统一事务/Outbox。真实 PaaS Gateway、权限服务和 RN 真机验证也未完成。这些是下一阶段，而不是隐藏限制。

## 3. 设计取舍回答模板

回答任何技术选型时使用四步：业务约束是什么；当前方案解决什么；付出什么代价；什么条件下会换方案。

示例：选择 SSE，因为当前是单向、可回放事件流，HTTP 部署简单；代价是双向能力弱；如果出现高频双向协作或二进制流，再切 WebSocket，但 Event Protocol 和 sequence 语义不变。
